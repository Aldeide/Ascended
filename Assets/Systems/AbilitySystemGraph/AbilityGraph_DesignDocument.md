# Design Document: Ability Graph (Unity Graph Toolkit + Job System)

## 1. Overview
This design leverages the **Unity Graph Toolkit (GTK)** for the authoring environment in Unity 6.4, but critically separates the **Authoring Data** from the **Runtime Execution Data**. To achieve maximum performance and zero per-frame allocation, the runtime graph execution will be powered by the **C# Job System and Burst Compiler** acting as a lightweight Virtual Machine (VM).

## 2. Critical Flaws in Standard Graph Traversal
A standard `GraphRunner` that traverses reference types (objects) at runtime has several bottlenecks:
1. **Cache Misses**: Nodes scattered across the managed heap destroy CPU cache coherence.
2. **Virtual Dispatch**: Polymorphic `Evaluate()` calls add significant overhead.
3. **Garbage Collection**: Temporary data passed between nodes often allocates memory.
4. **Job System Incompatible**: Reference types and arrays of objects cannot be passed into Unity Jobs.

## 3. High-Performance Architecture

To solve these issues, we adopt a **Baking Architecture**.

### 3.1 Editor Phase: Authoring (GTK)
- **`AbilityGraphAsset`**: The ScriptableObject used purely for authoring in the Unity Editor.
- **Default Nodes**: Contains unremovable `ActivateAbility` and `EndAbility` nodes.
- **GTK Nodes**: High-level, developer-friendly nodes (e.g., `Calculate Damage`, `Branch`).

### 3.2 Compilation Phase: Graph Baking
When an ability is saved or the game is built, the GTK graph is "Baked" into a flat, unmanaged data structure.
- **Node to OpCode**: Each logical node is compiled into an `Instruction` struct containing an `OpCode` (e.g., `ADD_FLOAT`, `CHECK_TAG`, `WAIT_TIME`) and memory addresses.
- **Memory Layout**: We allocate a flat `NativeArray<Instruction>` for the logic, and `NativeArray<float>` / `NativeArray<int>` for the local graph memory (variables, port values).
- **The Result**: A serialized byte array or `ScriptableObject` containing strictly unmanaged structs, perfectly contiguous in memory.

### 3.3 Runtime Phase: Burst-Compiled Graph VM
The `GraphRunner` is replaced by a Burst-Compiled Job struct (e.g., `AbilityExecutionJob`).
- **The VM Loop**: The Job iterates over the `NativeArray<Instruction>` using an Instruction Pointer (IP).
- **Execution Flow**: "Branch" nodes simply change the Instruction Pointer (like a `goto`).
- **Data Resolution**: Math and logic nodes read/write directly to indices in the local memory arrays. No backwards traversal is needed because the "Bake" step topologically sorts data dependencies to be calculated *before* they are needed.

## 4. Handling Main Thread Dependencies
The Job System cannot execute everything (e.g., playing Audio Cues, applying Networked Effects, instantiating GameObjects). 
- **Command Queues**: When the VM hits an action node like `ApplyEffect`, it writes a request struct into a `NativeQueue<AbilityCommand>`.
- **Sync Point**: After the Job completes its tick, the main thread reads the `NativeQueue` and executes the heavy Unity-side API calls.

## 5. Development Milestones
1. **Editor Authoring**: Set up GTK windows, port definitions, and base nodes.
2. **The Baker**: Write the compiler that translates the GTK graph connections into a flat `Instruction` array and topologically sorts data nodes.
3. **The Burst VM**: Implement the `AbilityExecutionJob` with a switch statement handling core opcodes (Math, Logic, Branching).
4. **Command Buffer Execution**: Implement the main thread dispatcher that resolves commands generated by the Job (Cues, Effects).
5. **Testing & Profiling**: Validate that execution produces 0 bytes of GC and executes in sub-millisecond times using the Profiler.

## 6. Testing Plan
- **Editor / Validation Tests**: Verify GTK persistence and structural integrity.
- **Compiler Tests**: Ensure the Baker produces the correct opcodes and correctly sorts dependencies. (e.g., A graph adding 2+2 should produce memory loading instructions followed by an ADD instruction).
- **Runtime Traversal (PlayMode)**: Unit tests comparing the output of the Job-based VM against expected logic flows.
- **Performance Thresholds**: Automated performance tests to assert that executing 1,000 graphs simultaneously takes less than 1ms on the main thread via Jobs.
